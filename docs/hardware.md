spi_flash: detected chip: boya

**结论：N16R8 规格属实。**

### AHT20 + BMP280 模块验证

接线 `VDD->3V3 / GND->GND / SDA->GPIO4 / SCL->GPIO5`，实测通过：

```
扫描 I2C 总线 (SDA=GPIO4, SCL=GPIO5) ...
  发现设备: 0x38  <- AHT20
  发现设备: 0x77  <- BMP280/BME280
AHT20  温度  28.61 C   湿度  48.82 %RH
BMP280 温度  27.95 C   气压 1004.08 hPa
```

- **BMP280 实测地址为 `0x77`**（不是 0x76），chip id `0x58` = 确为 BMP280 而非 BME280
- 两颗温度读数相差 0.5–0.7 °C，属正常范围
- 气压 1004 hPa 合理 → **Bosch 补偿算法实现正确**
- 哈气后湿度从 46% 升到 57%，随后平滑单调回落（56.4→54.1→52.3→51.1→50.3→49.6）
  → 传感器能正确跟踪真实物理过程
- 多次 30–45 秒连续运行，**I2C 错误 0 次，读取失败 0 次**

### 排查记录：模块初次接入时的间歇性故障

初次接线时症状为：正常读数约 7 秒 → 两颗传感器**同时** NACK → 总线 hardware timeout 卡死。
换到另一台主机复现相同症状，排除开发板因素。

**根因：模块 4 pin 排针虚焊。** 重新焊接后完全正常。

诊断要点：两颗独立的传感器同时失效，说明问题在两者共用的 4 根线上而非芯片本身；
且故障从 NACK（线断开、被上拉拉高）演变为总线被拉死（低电平），指向 **GND 断开** ——
模块失去参考地后，SDA/SCL 会经芯片内部 ESD 二极管找回路，把总线往低拽。

## 2. 引脚定义

丝印与乐鑫官方 ESP32-S3-DevKitC-1 完全一致。以 USB 口朝右、元件面朝上为基准：

**下排（22 pin，左 → 右）**

```
3V3  3V3  RST  4  5  6  7  15  16  17  18  8  3  46  9  10  11  12  13  14  5Vin  GND
```

**上排（22 pin，左 → 右）**

```
GND  TX  RX  1  2  42  41  40  39  38  37  36  35  0  45  48  47  21  20  19  GND  GND
```

说明：

- `TX` / `RX` = **GPIO43 / GPIO44**（UART0）
- `RST` = 芯片复位（EN），非 GPIO
- `5Vin` 默认为**输入**；如需从该脚输出 5 V，见 §3 焊盘跳线
- 数字即 GPIO 编号

## 3. 板载外设与焊盘跳线

| 接口 | 说明 |
|---|---|

| `RST` 按键 | 复位 |
| RGB LED | WS2812 系列可编程彩色 LED；**GPIO 编号待核实**（此类板多为 GPIO48，DevKitC-1 v1.0 为 GPIO38） |

### 三处焊盘跳线（0 Ω 电阻或直接短接）

| 跳线 | 出厂状态 | 作用 |
|---|---|---|
| `IN-OUT` | 断开 | 短接后 `5Vin` 引脚**输出** 5 V（供外部模块取电） |
| `RGB` | **默认已连接** | 断开后可释放该 GPIO 作普通 IO 使用 |
| `USB-OTG` | 断开 | 短接后丝印 `USB` 的 Type-C 口支持 **OTG 主机功能** |

### 烧录方式

1. 常规：接 `COM` 口，直接 `idf.py flash monitor`。
2. 原生 USB 口：**按住 BOOT 再上电**即可枚举出下载端口。

## 4. 重要注意事项

### 4.1 GPIO 33–37 被 Octal PSRAM 占用 ⚠️

N16R8 采用**八线（Octal）PSRAM**，会占用 **GPIO33 ~ GPIO37**。

排针上虽然引出了 **35 / 36 / 37**，但只要启用 PSRAM 就**不可作为普通 GPIO 使用**，误用会导致
PSRAM 访问异常或直接崩溃。做引脚分配时必须避开。

### 4.2 GPIO19 / GPIO20 与原生 USB 冲突

这两脚是原生 USB 的 D-/D+。若使用 USB-Serial-JTAG 或 USB-OTG，则不能再作普通 GPIO。

### 4.3 Strapping 引脚

`GPIO0`（BOOT）、`GPIO3`、`GPIO45`、`GPIO46` 为 strapping 脚，上电瞬间的电平会影响启动模式。
外接电路时避免在这些脚上加强上/下拉。`GPIO46` 另为仅输入（input-only）。

## 5. ESP-IDF 关键配置

`menuconfig` 中必须与硬件对应，否则 PSRAM 不可用或启动失败：

```
# Serial flasher config
CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y
CONFIG_ESPTOOLPY_FLASHMODE_QIO=y
CONFIG_ESPTOOLPY_FLASHFREQ_80M=y

# Component config → ESP PSRAM
CONFIG_SPIRAM=y
CONFIG_SPIRAM_MODE_OCT=y          # 关键：八线模式，N16R8 必须选 OCT
CONFIG_SPIRAM_SPEED_80M=y
```

分区表需按 16 MB Flash 重新规划（默认分区表按 2 MB 设计，会浪费绝大部分空间）。

## 7. 外接模块：ST7789 SPI 屏（240×320）

| 项目 | 参数 |
|---|---|
| 驱动 IC | ST7789 / ST7789V |
| 面板 | IPS，**240 × 320**，横屏使用为 **320 × 240** |
| 接口 | SPI，7~8 pin |
| 工作电压 | 3.3 V |

> 2026-08-07 之前用的是 1.9" 的 **170 × 320** 版本。两者驱动 IC 相同、接线相同，
> 只差一个列偏移和可见高度 —— 见下面的「坑一」。

### 接线

| 屏丝印 | 开发板 | 说明 |
|---|---|---|
| GND | GND | |
| VCC | **3V3** | 不要接 5Vin |
| SCL / SCK | **GPIO12** | SPI2 IOMUX `FSPICLK` |
| SDA / MOSI | **GPIO11** | SPI2 IOMUX `FSPID` |
| RES / RST | **GPIO13** | |
| DC / RS | **GPIO14** | |
| CS | **GPIO10** | SPI2 IOMUX `FSPICS0`；无此脚则不接 |
| BLK / LED | **GPIO9** | 背光 PWM；也可直接接 3V3 常亮 |

选脚原因：SCK / MOSI / CS 用的是 SPI2(FSPI) 的 **IOMUX 原生引脚** —— 走 IOMUX 才能跑到
80 MHz，换成其他脚会自动经 GPIO 矩阵转发，上限降到 40 MHz，满屏刷新时间翻倍。
其余脚避开了 Octal PSRAM 的 33–37、原生 USB 的 19/20、strapping 的 0/3/45/46，
以及 AHT20/BMP280 占的 4/5（两个模块可同时挂）。9–14 在下排是连续 6 个脚，接线顺手。

改引脚只需改 `main/display.h` 顶部的 `DISP_PIN_*`。

### ⚠️ 坑一：列偏移只对窄屏才需要

ST7789 的显存固定是 **240 × 320**。现在这块面板正好是满 240 × 320，
所以 **gap = (0, 0)**，不要设偏移。

换成 **170 × 320** 那种窄屏时才要设：那种面板只有 170 列，是**居中**贴在 240 列的
显存上的，列地址必须整体偏移 `(240 - 170) / 2 = 35`，否则画面错位、边缘出现花条。
横屏（`swap_xy`）之后这 35 落到 y 轴上，即 `esp_lcd_panel_set_gap(panel, 0, 35)`；
竖屏用则是 `set_gap(panel, 35, 0)`。

**换屏时这是最容易漏的一处**：`DISP_GAP_Y` 忘了从 35 改回 0，画面照样能正常显示，
只是整体偏了 35 行、并且下面 35 行永远刷不到 —— 看起来就像「边缘被浪费了」。
`DISP_H` 也要一起从 170 改成 240，否则只用了 240 行里的 170 行。

### ⚠️ 坑二：RGB565 要按大端存

ST7789 走 SPI 时按**大端**接收 16 位像素（高字节先出），而 DMA 是照内存顺序逐字节
发的。小端机器上直接存 `0xF800`（红），发出去的是 `0x00` `0xF8`，屏上解成 `0x00F8`
—— 变成暗蓝。

`esp_lcd` **没有**字节序开关：它的 `rgb_ele_order`（RGB/BGR）设的是 MADCTL 里的
红蓝**通道**顺序，不是字节序，改它解决不了这个问题。ESP-IDF 的 LVGL 移植都要开
`LV_COLOR_16_SWAP=1`，就是同一件事。

本项目的做法：**帧缓冲里一律存字节交换后的值**。

- `display.h` 的 `RGB565()` 宏内置 `__builtin_bswap16`，常量在编译期折叠，零开销
- `nes_emu.c` 拿到 nofrendo 的调色板后，把 256 个表项一次性换好，
  每像素查表时不额外花时间

**怎么认出这个症状**：颜色不是简单的红蓝互换，而是整体错乱且**绿色也会变**。
红蓝互换（BGR 问题）时绿色保持不变 —— 这是区分两者的关键。
实测现象：天空浅蓝→黄绿，草绿→暗红，橙棕→蓝紫。

### ⚠️ 坑三：IPS 屏要开反色

ST7789 的 IPS 屏基本都需要 `esp_lcd_panel_invert_color(panel, true)`，
否则显示为底片效果（黑白颠倒）。TN 屏多数相反。

### 配置速查

`main/display.h` 顶部的宏，显示不正常时**每次只改一个**：

| 现象 | 改哪个 |
|---|---|
| 画面偏移 / 边缘花条 | `DISP_GAP_X` / `DISP_GAP_Y`（满屏 240×320 用 0；170 列的窄屏用 35） |
| 上下或左右颠倒 | `DISP_MIRROR_X` / `DISP_MIRROR_Y` |
| 颜色像底片 | `DISP_INVERT_COLOR` |
| 红蓝互换 | `DISP_BGR_ORDER` |
| 花屏 / 雪花 | `DISP_SPI_HZ` 降到 40 MHz 或更低 |

### 性能（实测 2026-08-04，当时是 320×170 的屏）

满屏 320×170 RGB565 = 870,400 bit。

| 配置 | 每帧 | 满屏 fps |
|---|---|---|
| SPI 40 MHz + CPU 160 MHz + 单缓冲 | 30.3 ms | 33 |
| SPI 80 MHz + CPU 240 MHz + 双缓冲 | **11.6 ms** | **86** |

三处优化，按收益排序：

1. **双缓冲 + 核 1 推屏任务**（`display.c`）—— 收益最大。
   `esp_lcd_panel_draw_bitmap` 在发下一条带的 CASET/RASET/RAMWR 之前必须等上一条
   数据传完（命令与数据共用总线），所以推屏整体是阻塞的。单缓冲时画图和推屏只能
   串行相加；双缓冲后每帧耗时变成 `max(画图, 推屏)`。
2. **SPI 40 → 80 MHz** —— 传输时间 21.8 ms 减半到 10.9 ms。
   前提是 SCK/MOSI/CS 走 IOMUX 原生脚，否则 GPIO 矩阵限死在 40 MHz。
3. **CPU 160 → 240 MHz** —— `sdkconfig` 默认给的是 160，白扔 1/3 算力。

实测 11.6 ms / 理论 10.9 ms = **95% 总线效率**，剩下 0.7 ms 是每条带的开销。
已经贴着硬件上限，再优化空间不大。

**画图只占 2.0 ms，CPU 余量 83%** —— 这是留给模拟器的预算。

#### 每条带的开销到底是多少（实测 2026-08-09）

上面那句「0.7 ms 是命令开销」当时没记是几条带，后来做条带流式推屏时才专门量了一次。
固定推 256×192（98,304 字节，理论 9.83 ms），只改 `BAND_LINES`：

| 条带数 | 4 | 8 | 12 | 24 |
|---|---|---|---|---|
| 实测每帧 | 10.34 ms | 10.83 ms | 11.31 ms | 12.78 ms |
| 理论之外 | 0.51 ms | 1.00 ms | 1.48 ms | 2.95 ms |

完美线性，**斜率 122 µs/条带，每帧固定开销约等于 0**。

122 µs 远不是命令本身的总线时间（CASET+RASET+RAMWR 才 11 字节，只值约 1 µs），
而是每次 `esp_lcd_panel_draw_bitmap` 的驱动/ISR/信号量往返。而且它是**串行叠加**在
总线时间上的 —— 因为发下一条带的命令前必须等上一条数据传完，总线在这期间是空的。

结论：**条带越少越快**，只受条带缓冲内存和流水粒度约束。这个数字直接决定了后面
条带流式方案取 32 行/条而不是 16 行/条（差 0.86 ms）。

### NES 模拟实测（2026-08-04）

**稳定锁 60 fps，每帧 8.6 ms，CPU 余量 49%。**

分阶段耗时（`DIAG_TIMING=1` 打开诊断得到），vidbuf 在 PSRAM 时：

| 阶段 | 累计耗时 | 增量 |
|---|---|---|
| A 只跑 6502 CPU | 0.5 ms | — |
| B + PPU 渲染到 vidbuf | 9.0 ms | **+8.5 ms** |
| C + 调色板转换成 RGB565 | 11.8 ms | +2.8 ms |
| D + 推屏 | 12.4 ms | +0.6 ms |

推屏只加 0.6 ms —— 它跑在核 1 上，跟核 0 的模拟并行，这是双缓冲的收益。

### 画布优化：11.9 ms → 8.6 ms

上表里 B 那 8.5 ms 是因为 vidbuf（65 KB）当时被迫放在 PSRAM ——
内部 RAM 被两块 106 KB 的整屏帧缓冲占满了。

解法是**让帧缓冲只覆盖 NES 画面区**（`display.h` 的 `DISP_FB_W/H` = 256×168），
而不是整块 320×170 的屏。黑边由 `display_init()` 开机时清一次，之后再不碰。
三处收益一起来：

- 每块缓冲 106 KB → 84 KB，两块省下 44 KB，vidbuf 得以落回内部 SRAM
- 每帧少推 21% 的数据，撕裂窗口 10.9 ms → 8.6 ms
- 静止的黑边不用每帧重画

⚠️ 分配顺序要紧：`nes_emu_prealloc()` 必须在 `display_init()` **之前**调用。
两块帧缓冲一旦先占位，剩下的连续内部内存就凑不出 65 KB 了。

### 换 240 高的屏之后：画布 256×168 → 256×192（实测 2026-08-07，**已被下一节取代**）

> 这一节记的是「双缓冲整帧 RGB565」架构下的最后状态。2026-08-09 改成条带流式
> 之后，下面这些内存约束全部不再成立 —— 但推导过程仍然值得留着，因为它解释了
> 为什么非改架构不可。

**仍然稳定锁 60 fps，模拟+转换 12.0 ms/帧，CPU 余量 29%，内部 RAM 剩余 52 KB。**

面板从 320×170 换成 320×240，竖直方向多了 70 行可用。NES 裁掉 overscan 是 224 行，
论面积终于放得下 1:1 了 —— **但内部 RAM 放不下**。这是这次换屏真正的约束：

|  | 每块缓冲 | 两块合计 | 结果 |
|---|---|---|---|
| 256×224（1:1，理想） | 112 KB | 224 KB | ❌ 分配失败 |
| 256×208 | 104 KB | 208 KB | ❌ 分配失败 |
| **256×192（当时的选择）** | **96 KB** | **192 KB** | ✅ 剩 52 KB |

账是这么算的：能凑出大块的堆区标称 292 KB，到 `app_main` 时实际最大连续空闲块约
268 KB；vidbuf 先占 64 KB，剩约 204 KB 给两块缓冲 —— 每块上限约 102 KB，即 200 行。
再留点余量给 nofrendo 自己的小块分配（开 PSRAM 后 16 KB 以下的 `malloc` 仍优先走内部
RAM），取 192 行。

顺带把 `CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL` 从默认 32 KB 降到 8 KB：那是给
WiFi/BT 这类必须用内部 DMA 内存的驱动留的池子，本项目两样都不用。

于是竖向抽行从「每 4 行丢 1 行」（224→168）放宽到「每 7 行丢 1 行」（224→192），
画面高了 14%，缩放损失也小了。左右仍是各 32 列黑边（256 vs 320），上下各 24 行。

#### ⚠️ 帧缓冲不能放 PSRAM

试过把两块缓冲挪到 PSRAM 以换取 1:1 的 224 行，**行不通**：
`spi_master.c` 的 `setup_priv_desc()` 用 `esp_ptr_dma_capable()` 判断缓冲能否直接 DMA，
而那个函数只认内部 DRAM 地址段（`SOC_DMA_LOW`/`SOC_DMA_HIGH`），PSRAM 指针一律
返回 false。于是驱动会**每条带**临时 `malloc` 一块内部 DMA 缓冲再 `memcpy` 过去 ——
每帧多拷一整屏，还要每秒 240 次分配/释放 28 KB，数据最后照样落在内部 RAM。

反过来把 vidbuf 放 PSRAM、帧缓冲留内部更亏：vidbuf 是 PPU 逐扫描线读写的最热内存，
挪到 PSRAM 会让 PPU 渲染从 2 ms 涨到 8.5 ms（见上一节）。

想真正做到 1:1 的 224 行，只能改架构 —— 见下一节。

> ⚠️ 当时这里写的方案是「单缓冲 + 边转换边推的追赶式推屏，代价是每帧从
> `max(画图, 推屏)` 变成两者首尾相接」。**那个方案是错的**：首尾相接就是
> 8 ms + 14 ms = 22 ms，直接超出 60 fps 的 16.67 ms 预算，根本跑不动。
> 正确的做法是把双缓冲下移一层，见下。

### 条带流式推屏：画布 256×192 → 288×224（实测 2026-08-09）

**稳定锁 60 fps。核 0 模拟 8.1 ms（余量 52%），核 1 推屏 14.03 ms，内部 RAM 剩余 142 KB。**

| | 改之前 | 改之后 |
|---|---|---|
| 分辨率 | 256×192（每 7 行丢 1 行） | **288×224（竖向 1:1，不抽行）** |
| 像素宽高比 | 1.00（偏窄 12%） | **1.125（对 8:7 误差 1.6%）** |
| 黑边 | 左右 32 / 上下 24 | 左右 16 / 上下 8 |
| 核 0（6502+PPU） | 12.0 ms，余量 29% | **8.1 ms，余量 52%** |
| 核 1 推屏 | 10.4 ms | 14.03 ms |
| 帧时间 `max()` | 12.0 ms（占 60fps 预算 72%） | 14.03 ms（**84%**） |
| 内部 RAM 剩余 | 52 KB | **142 KB** |

#### 关键点：双缓冲下移到 8 位 vidbuf

前面几节一直在算「两块 RGB565 整帧缓冲塞不塞得进内部 RAM」，而真正的出路是
**根本不要整帧 RGB565 缓冲**：

- `display.c` 只留两块 288×32 的条带缓冲（各 18 KB），核 1 把第 N+1 条转换进一块的
  同时 DMA 正在推第 N 条，两者流水。整块画布由回调按条带现算，不落地。
- 双缓冲没有消失，只是**下移到了 8 位的 NES vidbuf 那一层**（每块 64 KB，比 RGB565
  便宜一半）。核 0 渲染一块的同时核 1 读另一块，帧时间仍然是 `max(模拟, 推屏)`。

内存账：

| | 旧（整帧双缓冲） | 新（条带流式） |
|---|---|---|
| vidbuf | 1 × 63.75 KB | 2 × 63.75 = 127.5 KB |
| RGB565 帧缓冲 | 2 × 96 = 192 KB | — |
| 条带缓冲 | — | 2 × 18 = 36 KB |
| **合计** | **255.8 KB** | **163.5 KB** |

省下 92 KB，同时分辨率还涨了。这块余量正是将来接 I2S 音频要用的。

#### 每帧换 vidbuf 是安全的

`nes_setvidbuf()` 就是个指针交换（`nes.c`），而 nofrendo 调完 `blit_func` 之后本帧
不再碰 vidbuf（后面只剩 `apu_emulate()`）。所以在 blit 回调里把刚画完的那块交给
核 1、然后立刻换到另一块，下一帧的 `ppu_renderline` 就写进新的那块，互不干扰。

#### 为什么是 288 而不是 320

不是内存不够了 —— 是 SPI 带宽。288×224 已经占掉 60 fps 预算的 84%，
铺满 320×240 要 16.2 ms，占 **97%**，只能靠掉到 30 fps 换。而 NES 跳帧会让
「超过 8 精灵/扫描线时靠逐帧轮换实现的闪烁」永久消失 —— 2:1 跳帧每次采样同一相位，
本该在奇数帧出现的精灵会**彻底看不见**（魂斗罗的子弹、忍者龙剑传的敌人）。
代价远大于消掉那 16 像素黑边。

而 288 = 256 × 9/8 顺手把 NES 的 8:7 像素宽高比修对了（误差 1.6%），
反倒是拉满 320 的 PAR 1.25 偏宽 9%，更差。

### 撕裂

这块屏只有 8 个脚，**没有引出 TE（tearing effect）信号**，所以没法做硬件垂直同步——
推屏和面板自身的扫描节奏是各走各的，画面剧烈变化时会看到撕裂。
只能靠缩短推屏窗口来减轻。

推屏窗口的历史：320×170 整屏 10.9 ms → 画布 256×168 后 8.6 ms → 256×192 后 10.4 ms
→ **288×224 后 14.0 ms**。最后这次为了画面尺寸和宽高比，撕裂窗口长了 35%，
是这次改动唯一的退步。

换屏时如果新屏引出了 TE 脚，接一个 GPIO 做中断同步就能彻底消除。

## 8. 可用 GPIO 一览

排除已占用和不可用的脚之后，还剩这些可以自由分配（接手柄按键、I2S 音频等）：

**完全自由（19 个）**

```
1  2  4  5  6  7  8  15  16  17  18  21  38  39  40  41  42  47  48
```

**已占用**

| 引脚 | 占用方 |
|---|---|
| 9, 10, 11, 12, 13, 14 | ST7789 屏（BLK / CS / MOSI / SCK / RST / DC） |
| 33–37 | Octal PSRAM，启用 PSRAM 后不可作普通 IO |
| 19, 20 | 原生 USB D- / D+ |
| 43, 44 | UART0 TX / RX（串口日志） |

**能用但要小心**

| 引脚 | 注意 |
|---|---|
